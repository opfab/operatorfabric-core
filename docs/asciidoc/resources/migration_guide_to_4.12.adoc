= Migration Guide from release 4.11.X to release 4.12.0

== Service renamed: cards-external-diffusion to email-gateway

The `cards-external-diffusion` service has been renamed to `email-gateway` to better reflect its purpose as an email gateway for card notifications. This change affects multiple aspects of your deployment.

=== Docker image name

The Docker image name has changed:

* `of-cards-external-diffusion` is now `of-email-gateway`

Update your docker-compose.yml file accordingly


=== Configuration file name

The service configuration file has been renamed:

* `cards-external-diffusion.yml` is now `email-gateway.yml`

Update your volume mount in docker-compose.yml:

Replace
----
    volumes:
      - "./services/cards-external-diffusion.yml:/usr/app/config/docker.yml"
----

With

----
    volumes:
      - "./services/email-gateway.yml:/usr/app/config/docker.yml"
----

=== Configuration parameters

All configuration parameters have been renamed from `cardsExternalDiffusion` to `emailGateway`:

Replace
----
operatorfabric:
  cardsExternalDiffusion:
    adminPort: 2106
    activeOnStartup: true
    customHandlebarsHelpersFile: config/customHandlebarsHelpersExample.js
    defaultConfig:
      mailFrom: opfab@localhost.it
      # ... other config
----

With

----
operatorfabric:
  emailGateway:
    adminPort: 2106
    activeOnStartup: true
    customHandlebarsHelpersFile: config/customHandlebarsHelpersExample.js
    defaultConfig:
      mailFrom: opfab@localhost.it
      # ... other config
----

Additionally, mail server configuration parameters have been moved under the `emailGateway` section:

Replace
----
operatorfabric:
  mail:
    host: localhost
    port: 1025
    auth:
      user: guest
      pass: guest
----

With

----
operatorfabric:
  emailGateway:
    smtpServer:
      host: localhost
      port: 1025
      auth:
        user: guest
        pass: guest
----

Furthermore, email configuration parameters under `defaultConfig` have been reorganized under an `outgoingEmails` section:

Replace
----
operatorfabric:
  emailGateway:
    defaultConfig:
      mailFrom: opfab@localhost.it
      subjectPrefix: 'Opfab card received '
      bodyPrefix: 'You received a card in opfab : '
      # ... other email config
----

With

----
operatorfabric:
  emailGateway:
    defaultConfig:
      outgoingEmails:
        mailFrom: opfab@localhost.it
        subjectPrefix: 'Opfab card received '
        bodyPrefix: 'You received a card in opfab : '
        # ... other email config
----

=== MongoDB collection name

The MongoDB collection name has changed:

* `cardsExternalDiffusion-mailsAlreadySent` is now `emailGateway-emailsAlreadySent`. This collection stores records of emails that have already been sent to prevent duplicate notifications. To avoid sending duplicate emails, you should rename the collection in your MongoDB database after stopping Opfab and before starting the new version:

----
db["cardsExternalDiffusion-mailsAlreadySent"].renameCollection("emailGateway-emailsAlreadySent")
----

Alternatively, you can delete the existing collection after migration (the new collection will be created automatically):

----
db["cardsExternalDiffusion-mailsAlreadySent"].drop()
----

=== Nginx proxy configuration

If you have custom nginx proxy configuration referencing the service, update the location path:

Replace
----
  location /cards-external-diffusion/ {
    proxy_set_header Host $http_host;
    proxy_pass http://cards-external-diffusion:2106/;
  }
----

With

----
  location /email-gateway/ {
    proxy_set_header Host $http_host;
    proxy_pass http://email-gateway:2106/;
  }
----

=== CLI and scripts

If you use the OperatorFabric CLI to manage logs or other operations, the service name has changed:

* Use `email-gateway` instead of `cards-external-diffusion` in CLI commands

For example:
----
./opfab logs email-gateway
----

=== Menu Configuration via REST API

The menu configuration, previously managed through the ui-menu.json file on the server filesystem, is now exposed via a
dedicated REST API allowing retrieval (GET) and update (POST) of the full configuration. This aligns the menu management
with the existing configuration mechanism used for other files, for example `processgroups`. +

The API endpoint is `/businessconfig/uimenu`:
----
GET /businessconfig/uimenu
POST /businessconfig/uimenu
----
Example update:
----
curl -X POST "$OPFAB_URL/businessconfig/uimenu" \
  -H "Content-Type: application/json" \
  -d `@uimenu.json`
----

You can also do it using the cli (command line interface), for example: `opfab ui-menu load <uiMenuFileName>`

Additionally, within the `locales` section, the `i18n` property has been renamed to `localizedContent`
(e.g. "i18n": { ... } becomes "localizedContent": { ... }). No other structural changes have been introduced.

== Card API endpoints updated to use query parameters

To properly handle card IDs containing special characters (especially slashes `/`), the card consultation and deletion endpoints now use query parameters instead of path parameters.

=== Affected endpoints

The following endpoints are now deprecated and will be removed in a future release:

* `GET /cards-consultation/cards/{id}` - replaced by `GET /cards-consultation/cards?cardId={id}`
* `DELETE /cards-publication/cards/userCard/{id}` - replaced by `DELETE /cards-publication/cards/userCard?cardId={id}`
* `DELETE /cards-publication/cards/{id}` - replaced by `DELETE /cards-publication/cards?cardId={id}`

The deprecated endpoints will continue to work for backward compatibility, but a deprecation warning will be logged when they are used.

=== Why this change?

Even when URL-encoded (e.g., `/` as `%2F`), Spring Framework interprets slashes in path parameters, which causes issues when card IDs contain this character. Using query parameters resolves this issue and allows card IDs to contain any special character.

=== Impact on custom integrations

If you have custom code or scripts that call these endpoints directly (not using the OperatorFabric web UI or CLI), you need to update them to use the new query parameter format:

*Before:*
----
GET /cards-consultation/cards/myProcess.instance
DELETE /cards-publication/cards/userCard/myProcess.instance
DELETE /cards-publication/cards/myProcess.instance
----

*After:*
----
GET /cards-consultation/cards?cardId=myProcess.instance
DELETE /cards-publication/cards/userCard?cardId=myProcess.instance
DELETE /cards-publication/cards?cardId=myProcess.instance
----

Remember to properly URL-encode the card ID when calling these endpoints. For example, a card ID containing a slash like `myProcess/instance` should be encoded as `myProcess%2Finstance` in the query parameter.

== Card API endpoints updated to use request body or query parameters

Several additional card endpoints have been updated to properly handle card UIDs containing special characters. These are breaking changes without backward compatibility.

=== Affected endpoints

The following endpoints have been changed:

* `POST /cards-publication/cards/resetReadAndAcks/{uid}` - now `POST /cards-publication/cards/resetReadAndAcks` with JSON body
* `POST /cards-publication/cards/userAcknowledgement/{cardUid}` - now `POST /cards-publication/cards/userAcknowledgement` with JSON body
* `POST /cards-publication/cards/cancelUserAcknowledgement/{cardUid}` - now `POST /cards-publication/cards/cancelUserAcknowledgement` with JSON body
* `POST /cards-publication/cards/userCardRead/{cardUid}` - now `POST /cards-publication/cards/userCardRead` with JSON body
* `DELETE /cards-publication/cards/userCardRead/{cardUid}` - now `DELETE /cards-publication/cards/userCardRead?cardUid={cardUid}` with query parameter

These endpoints are used internally by the OperatorFabric web UI and are not typically called directly by external integrations. No backward compatibility is provided for these endpoints.

=== Impact on custom integrations

If you have custom code or scripts calling these endpoints directly, you must update them to use the new request format. The OperatorFabric web UI, CLI, and internal services have all been updated to use the new format.
